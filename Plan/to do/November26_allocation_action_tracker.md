## Findings from the existing implementation

- Whole-month CP-SAT, reviewed alternatives, scoped repairs, locks, independent final validation, durable proposal revisions, and atomic application already exist. Extend them rather than build a competing generator.
- `template_compute.py` explicitly replays a **sequential** template planner. Parallel ranking of numeric rows does not make dependent unit decisions globally balanced.
- WebGPU already supports member scoring, template ranking, and optimizer seed hints. CP-SAT search remains on the backend CPU. GPU hints do not certify a whole-month solution.
- Recorded member benchmark: approximately 215 ms server versus 410 ms local GPU. A separate 96-member synthetic benchmark found large backend caching gains. Neither establishes current production performance, nor the performance of template/optimizer workloads.
- Ollama/Qwen is an optional interpretation assistant; approved-example retrieval and a three-weight preference learner are separate mechanisms. Existing evidence is insufficient to claim fewer real departmental corrections.
- Leave requests, manual management, calendars, reviewed approvals, and profile leave listings already exist. Build an integrated history/statistics view on those canonical records; do not create a second leave database.
- The later call-level-pool contract explicitly amends earlier strict-single-level wording. Preserve deliberate mixed-level pools, effective-date eligibility, pro-rata fairness, campus-last policy, and existing exception attribution unless an explicit policy amendment is approved.
- No dedicated weekly OT-demand configuration was identified in the examined unit, leave, and allocation paths. Confirm this inventory before adding schema or UI.

## Architecture and proposed policy boundaries

1. **One scheduling context:** versioned rules + dated postings/call levels + leave + duty/rest intervals + OT demand + holiday/closure exceptions + protected existing assignments. Every relevant change invalidates affected previews and benchmarks.
2. **Two linked feasibility problems:** retain enough compatible people for OT, and assign eligible people to duties. Prefer joint month-wide modeling; benchmark an iterative template/person repair approach as a lower-cost alternative. Choose using acceptance evidence, not GPU availability.
3. **OT staffing arithmetic:** derive availability from distinct person identities and time intervals. A person unavailable through both leave and post-duty rest is removed once. OT demand is an eligible-person reservation, not simply an area count. Overlapping call pools and simultaneous areas require matching/assignment feasibility, not independent totals that reuse the same person.
4. **Demand and minima:** proposed default is to satisfy both existing staffing minima and OT requirements without adding them blindly. Whether a minimum represents additional reserve is a policy decision. Do not invent coverage with aggregate headcounts.
5. **Fairness:** retain approved per-call-level and partial-availability policy. Higher OT pressure should reduce that day's unit duty contribution where feasible; fair month-wide compensation must respect eligible capacity and must not penalize approved leave or silently rewrite personal targets.
6. **Multimodel scope:** multiple language models may propose interpretations, explanations, or independently critique a proposal. Agreement is not a safety proof. Deterministic optimization, independent checking, revision control, and transaction recovery govern allocation and recovery.
7. **No universal perfection claim:** an optimal result is relative to the modeled rules and candidate set. Missing data, unresolved policy, infeasible demand, and time-limited search remain visible. Existing explicit exception workflows remain separately attributed and never become automatic permissions.

## Tracker operating rules

- Status vocabulary: `Pending approval`, `Queued`, `Ready`, `In progress`, `Blocked`, `Verification`, `Done`, `Deferred`. Following approval, dependency-waiting items are `Queued`; the source review is not implementation completion.
- After approval, record exact scope/date below. Assign an owner and move dependency-ready items to `Ready`. Do not infer approval for unresolved policy choices, model installation, cloud processing, or production deployment.
- Update the relevant row on every state change and append an execution-log entry with evidence. No silent deletions or renumbering; added scope gets a separate change request, preserving this 50-item baseline.
- `Done` requires the row's acceptance evidence, applicable integration checks, reviewed user-visible behavior, no unexplained regression, and recorded rollback implications. Do not mark an item done because a component already exists or a synthetic example passed.
- `Blocked` needs a named blocker and next action. `Deferred` needs explicit user agreement and does not count as completed. Only `Done` increments completion; all 50 must be `Done` for this tracker to be complete.
- Evidence defaults to anonymized/disposable fixtures. Operational data may be inspected only within authorized access; no destructive testing, migrations, imports, or repair application against live rota data during verification.
- Existing unrelated working-tree changes must be preserved. Snapshot the exact relevant revision/diff before each batch; avoid broad refactoring or unrelated UI rewrites.
