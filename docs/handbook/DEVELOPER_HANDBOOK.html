What the system does

Purpose, users and confirmed product decisions

The rota board of the Anaesthesia department (~220 doctors across several units and two campuses) uses this application to plan, check and publish the monthly on-call duty rota, and to analyse historical duty load.

① Members

Canonical names, aliases (spreadsheet spellings), designations and each doctor's default call level.

② Leave

Recorded manually or imported from the monthly leave spreadsheet; approved leave blocks duties.

③ Unit postings

Monthly Unit Management board: who is in which unit at which call level, plus DRP / SICU / Pain postings.

④ Rota generation

Stage 1 allocates every duty slot to a unit; stage 2 assigns a person (manual with suggestions, or safe auto-fill).

⑤ Review & publish

Warnings, overrides, fairness and swap requests are reviewed; the month is published with an approval note and exported to Excel.

⑥ Analysis

Historical data (Jan 2025 – May 2026) and published months feed a duty-load dashboard.

Where everything lives

Layering rule

API modules stay thin (validation, auth dependency, error mapping); all logic goes into services/; persistence through models/; schema changes through Alembic.

Architecture

Runtime components, layers and deployment shapes

API layer · app/api/v1

Declares request/response models, applies Depends(current_user) / Depends(require_admin) where present, validates month=YYYY-MM via month_bounds(), calls one service and maps ValueError, RotaAssignmentError, RotaReviewError, RotaPublishError to HTTP errors.

Service layer · app/services

All business rules. Services receive a Session and commit themselves. Many responses are plain dicts built by *_to_dict helpers.

Persistence

SQLAlchemy 2.0 typed ORM, UUID primary keys, naive UTC timestamps, JSON snapshots for audit. Alembic owns schema changes.

No background work

No job queue, cache or scheduler. Generation, auto-fill and historical import all run synchronously inside the HTTP request.

The monthly rota workflow

From members to a published Excel rota

StepScreenEndpointsService

3 Unit boardunits/unit-management/*, /unitsunit_management.py, unit_assignment_import.py

Publishing does not freeze the month (B1)

After publishing, slots and assignments can still be changed and the export is rebuilt from live data. Treat this as a known gap until a publish lock is implemented.

What happens at each stage

  1. Setup — GET /rota-setup/month gets or creates the RotaPeriod ("June 2026") and an empty scope, and reports per-unit readiness (members, call-level spread, leave). The board picks units and locks the scope.
  2. Generate — POST /rota-template/generate requires a locked scope; by default removes previously generated slots (refuses if any is assigned) and creates one slot per day × mandatory active duty, each allocated to a unit (§8.1). Every decision becomes a generation event.
  3. Assign — the day modal shows each slot's safety (§8.2) and ranked candidates (§8.4). Saving validates (§8.3); warnings need an override reason, blocked results cannot be saved. Safe auto-fill (§8.5) handles clean slots.
  4. Review — open slots, template-review slots, staffing warnings/hard blocks and overrides; accept warnings with a note; request/approve/reject exchanges; workload and fairness tables.
  5. Publish — checklist (§8.6); stores a RotaPublishApproval, sets the period to published and enables the final Excel export.

Core algorithms

Unit allocation, safety, validation, ranking, auto-fill and publishing

8.1 Template generation — unit allocation

services/rota_template.py · generate_empty_template → choose_balanced_unit → optimize_template_slot_layout

Fairness policies

equal_unit
every included unit gets the same target share
equal_people
share proportional to active eligible people
hybrid (default)
≈ half equal share, half proportional

Weights: allocation_target_weights. Background: docs/unit_slot_fairness_policy_modes.md, docs/unit_slot_imbalance_incident_report_2026_05.md.

8.2 Slot safety

services/rota_safety.py · slot_safety, safety_status

Rest rule gap (B2 — reproduced)

Rest is only checked backwards one calendar day, inside the month. A doctor with a 24h duty on the 13th can be given a 24h duty on the 12th with status clear; the 31st → 1st boundary is never checked; minimum_gap_after_24hr_hours only affects ranking and post_24hr_blocks_next_day_elective is not read anywhere.

8.3 Assignment validation

services/rota_assignment.py · validate_assignment, assign_person_to_slot

blocked — cannot be saved

slot full without “replace” · call-level mismatch · eligibility-group mismatch

needs_override — reason required

inactive member · not posted to the unit · leave / same-day / rest blockers · slot staffing warning or hard block · monthly limits (24h, weekend 24h, same family, same campus)

clear — saved directly

None of the above apply.

8.4 Candidate ranking

services/rota_candidates.py · candidate_score — lower score ranks higher

8.5 Safe auto-fill

Walks the month's slots in date order: skips filled slots; in strict mode skips slots whose required call level is ambiguous; assigns the first candidate that is eligible, validates clear, needs no override and (strict) matches the single required call level. Every decision is logged as an auto-fill event.

Performance (P1) & robustness (B12)

The full month context is rebuilt per slot and each candidate is fully re-validated, so a full month can take minutes inside one HTTP request. The run row is saved as completed before work starts and each assignment commits separately.

8.6 Publish checklist

Blockers

  • monthly scope not locked
  • no generated slots
  • open (unassigned) slots
  • hard-blocked review items
  • pending / needs-override exchanges

Warnings (need confirmation)

  • review items not accepted with a note
  • assignments saved with override reasons

Publish requires confirm_warnings=true when any are present.

Leave, units and imports

Every import follows preview → resolve → apply-safe-rows

Leave — leave.py, leave_import.py

  • Manual leave only for active members; end date ≥ start date.
  • Table sheets: header detected in the first 25 rows; columns recognised by name (name/person/doctor/member/staff, start/from/date, end/to, type, slot/session, status, notes). Otherwise a "wide calendar" layout with one column per day.
  • Half-day markers in name cells become leave_slot; duplicates and already-recorded leave are flagged and skipped.
Leave statusCalendarEffect on duties
approvedshownHARD BLOCK
requested, imported_pending_reviewshownWARNING
cancelled or anything else (incl. typos — B13)hiddenIGNORED

Unit Management — unit_management.py, unit_assignment_import.py

  • Board postings (source="unit_board") are what generation should use. Validation flags inactive members, members in more than one unit in a month, overlapping primary postings, missing unit or posting type.
  • Unit settings: unit-level minimum free people plus per-call-level minimums (validated against that month's counts).
  • Unitwise import: grid of units × posting sections, date ranges like 1-15, 1st to 15th or ISO ranges. Fuzzy matching thresholds: members 0.88, units 0.80, required lead over runner-up 0.04. Manual corrections are learned as aliases and unit mappings.
Replace existing (B6)

“Replace existing” deletes every board posting that overlaps the month — including postings that also cover other months.

Admin mappings and the department roster

Mappings

scan-historical collects duty, unit and posting labels from the historical workbooks and seeds suggested targets (classify_duty_label); admins review them on the Mappings screen.

Roster

Reconcile: rename to roster spelling, merge duplicates, add aliases/designations, create missing members. Reset: destructive wipe — never on a live database (B4, S3). Prefill call levels: from the May 2026 unitwise workbook.

How-to recipes

Common change patterns, step by step

➕ Add a new duty type

  1. Add to DUTY_TYPES in app/domain/duty_types.py (and MAIN_24HR_KEYS if it counts as a main 24h duty). Rules merge it in automatically on next read.
  2. Eligibility defaults: extend the PAC_SUBDIVISION_RULES-style dicts in rota_rules.py, or configure in Rota Rules.
  3. Historical parser: teach classify_duty_label in services/imports.py.
  4. Frontend groupings (DUTY_GROUPS, DUTY_TEMPLATE_GROUP_ORDER/LABELS) and export labels (EAGLE_EYE_GROUP_LABELS) for a new family.
  5. Tests in tests/test_rota_template.py.

⚙ Add a rule setting

Extend the pydantic model in services/rota_rules.py with a default (old JSON must still validate) → use it in the service → add to RotaPhaseOneRules in api.ts → add to the form in renderRotaRules() and the rule-* submit handler.

🔌 Add an endpoint

Service function in services/ → router function in api/v1/ with an auth dependency → register router in api/routes.py if new → client function in api.ts → tests.

🗄 Add a column or table

Model change + Alembic migration + read models / *_to_dict + tests. If it references persons, units, rota_periods or duty_slots, also update merges and the roster reset (B4).

🩹 Fixing a known issue

Search the code for KNOWN ISSUE (handbook <ID>), fix, add a regression test, then update the Inspection Report register and Plan/development_log.md.

Conventions and gotchas

Things that surprise new developers

#Gotcha
1Month strings are always YYYY-MM; month_bounds() validates them.
2Many GET endpoints create rows on first access (rota period, scope, default rules, default clusters).
3normalize_call_level folds Co-1st into 1st call and returns unknown strings unchanged.
4person_postings.posting_type holds a call level for board postings but a free label for historical ones.
5Template slot labels are "<UNIT_CODE>:primary"; uniqueness is per (period, date, duty, label).
6Datetimes are naive UTC; the frontend's default month uses UTC (toISOString).
7Services commit internally; composing services in one request does not give one atomic transaction.
8Dataset specifics are hard-coded (roster sheet names, May 2026 workbook, manual alias overrides, 2026-03-01 effective date) — search for 2026 before reusing code for a new year.
9Short non-24h duties default to 08:00→08:00 windows (B9) — check rule durations when touching timings.
10The frontend hides admin tools, but backend protection is per-endpoint and incomplete (S3).
