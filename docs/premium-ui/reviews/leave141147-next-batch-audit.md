The backend source was read only to establish existing semantics. `app.services.leave` defines active calendar statuses as approved, requested and imported_pending_review; only approved is blocking. `leave_day_entries` preserves each qualifying record per day. Summary daily totals count entries, while `people_on_leave` counts unique persons. The proposal therefore says “records” for entry counts and “People with leave records” for the unique-person metric. It does not deduplicate entries, change pressure ranking or manufacture unavailable people.

## Reviewable presentation candidate

`tmp/leave141147-status-proposal/` contains the saved before sources, proposed `main.ts`, an append-only theme fragment, `proposal.patch`, `source-manifest.json` and `source-proof.json`. `tmp/prepare_leave_status_proposal.py` creates this scratch material; `tmp/prove_leave_status_proposal.mjs` checks it.

The candidate adds two pure helpers for returned status counts and a plain-language day summary. It uses that summary for calendar accessibility, agenda headings and the day modal; adds textual per-day status counts that remain present on phones; explains approved versus pending semantics above the two calendar representations; and clarifies the unique-person metric/help text. Existing count numbers, array membership, order, busiest-day/pressure computation, preview truncation, buttons and API calls remain intact. All dynamic status words use the existing escape function.

The overlay compiler reports zero full-project TypeScript diagnostics. AST comparison confirms three assigned event handlers, 40 addEventListener calls, 95 imported API calls, 16 confirmation/serialization calls and 331 other function declarations are byte-identical. This is source evidence, not a runtime claim. The first compiler attempt resolved configured type packages from the repository root and failed; setting the compiler host's working directory to the real frontend project resolved that harness issue without changing application/dependency code.

This candidate is deliberately not ready for blind application. The seven-column calendar can grow substantially when several textual statuses wrap at 320px. Measure actual status text, selected day, controls, full-error readability and document/ancestor clipping before choosing the final compact treatment. Do not hide the labels merely to make a no-overflow assertion pass. A Day list remains the complete readable alternative, and its existing state/focus must survive toggles.

The baseline is the pre-close-icon `main.ts` and theme. The parent is preparing a separate close-icon/header target patch, so this candidate will require a context-based rebase against the later main/theme hashes. Preserve the saved before files and regenerate; copying this old whole main file would overwrite concurrent frontend work.
