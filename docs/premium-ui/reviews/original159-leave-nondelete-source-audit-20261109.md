Keep the text and eligibility unchanged.

2. After confirmation it executes **one** `cancelLeaveRequest(leave.id)`. The API function at 1895 sends POST `/api/v1/leave/requests/${id}/cancel` with literal body `"{}"`. After an accepted response, the handler rechecks ownership, shows `Leave cancelled`, and awaits **full `renderLeave()`**. On request failure while still owned it reports the existing error and resets the connected button. No automatic mutation retry exists. Preserve that.

3. Main 4148 exposes admin-only `data-approve-month-leave`, disabled when no returned records have status `requested` or `imported_pending_review` (case normalized only for the count). 5. API `request` captures auth generation, verifies it after headers and again after response-body decoding, and rejects session changes. Therefore absence of an extra local account guard inside the dialog is **not evidence that account-switched responses can be committed**. 6. Individual approval/rejection uses **Edit leave**, not a separate direct approve button in current monthly markup. ## Why the full refresh is a retention/recovery gap

`renderLeave()` at 4211 immediately assigns the complete root a skeleton. It reads calendar, requests and pressure concurrently, then replaces the complete root with `renderLeaveSnapshot()` and remounts import history. On any failure it replaces the root with `Leave could not load` and a route-level Try again button. Thus an accepted decision followed by failed readback has no retained last-known-record view. Even a successful read recreates the Day list control and pressure disclosure. `leaveCalendarView` is a module variable, so its chosen value can survive; disclosure `open` is DOM state and is lost. Selection is a Set and is pruned against the refreshed IDs; assert actual surviving selection rather than assuming full render necessarily empties it.

The existing `createDependentParentLifecycle` at 3292 already provides account/view/render/month/root/day-overlay ownership, latest-read arbitration, validated three-GET readback, stale-last-known status, read-only retry and partial replacement via `refreshProfileLeaveReadback`. The latter retains the Day list toggle control and pressure container/open state, updates affected content, refreshes the pending-approval count and synchronizes selection. The monthly snapshot prunes only IDs absent from returned records. Cancellation retains the cancelled record ID; no manual deletion-selection clearing is appropriate.

## Minimal candidate design

1. Cancellation: after existing native confirmation succeeds, capture a retained lifecycle before beginning the existing POST. After its accepted response and existing `current()` guard, keep the success toast and invoke `confirmed(); closed()` instead of full render. Creation before the POST captures the original owner, not a newer route. Leave all failures before accepted response on the existing catch path. Separate confirmed-write/readback failure language; GET failure must never become `Failed to cancel leave` or trigger another POST. Scope one lifecycle per accepted cancellation; existing latest-reader arbitration governs overlapping refreshes.

2. Monthly approval: capture a retained lifecycle alongside the current owner before opening the dialog. In the existing accepted callback, after current-owner guards, keep the returned-count toast and invoke `confirmed(); closed()` instead of full render. This small option requires **no dialog signature/API/payload change** and preserves immediate read timing: its callback already starts parent loading immediately before dialog.close. The asynchronous three-GET continuation runs after callback/close. Confirm actual focus restoration behavior; don't claim that `closed()` semantically means the approval dialog's close notification without testing. If readback must be deferred until an actual close event, add an optional lifecycle close hook explicitly, with cancel/close-without-confirmation producing zero parent reads; that is a broader option requiring its own compatibility matrix.

3. Keep any fallback full render limited to a provably unavailable retained lifecycle under the same existing owner; never refresh a newer route or account. Explicitly preserve the confirmation busy/close behavior and callbacks which currently drive original 142 monthly approval. Isolate any local lifecycle-start exception from accepted mutation semantics; don't let it encourage replaying an already accepted approval.

4. No backend, permission, scheduling, persisted status, export or API change is needed. One accepted mutation produces one three-GET parent read. Retry produces only those GETs. Preview is already a POST, so write-count assertions must distinguish review from actual approval mutation.
