## What the actual production helper does

`bindLeaveCalendarFocus` installs one delegated focus listener under the existing `bindViewEvents` AbortSignal. Existing login/logout/rebinding aborts that lifetime. New date focus first stops the previous owner; a pending controller then owns document-capture pointer/wheel/keydown listeners and the target focusout listener. Document capture also cancels work for newer intent outside the scroller. It does not prevent default keyboard input or focus another control.

Every tick requires the same exact active button, connected root/region/target, containment and no hidden/inert ancestor. The helper measures the real computed outline and positive offset, the region client clipping bounds and the full target rectangle. It applies instant horizontal-only scrolling with outward integer rounding and an extra pixel of clearance. Native `scrollBy` missing/throwing falls back to setting `scrollLeft`; if that also fails, the outer recovery path runs. There is no request, form/persistence operation, timer, vertical scroll or focus call in the helper.

The production stability signature includes target and scroller rectangle edges, client dimensions and scrollLeft, unlike the earlier injection's simpler scroll-position counter. Four stable, fitting frames end the owner; a monotonic one-second deadline bounds work. The source correctly discloses that its new listener/RAF/instant-scroll/recovery path is an exception to existing-effects parity. Previous diagnostic passes cannot be inherited as a runtime pass for this different implementation.

Recovery is tied to the existing help paragraph outside the month scroller. A WeakMap remembers the exact text and role, failure adds an actionable Day list hint with `role=status`, and later success can restore the exact original values. No HTML is interpolated into that message. This leaves the real Day list control available rather than creating a second data representation.

## Three required corrections before integration

1. **Make cancellation cleanup survive missing/throwing `cancelAnimationFrame`.** V6 aborts pending ownership but then calls `view.cancelAnimationFrame(frame)` without a feature check or catch, before clearing `frame` and `stopPending`. A failure can escape a native input/lifetime abort handler and leave cleanup bookkeeping stale. Capture the outstanding ID, clear frame/owner bookkeeping first, abort the signal, then feature-check and guard frame cancellation. A callback that cannot be cancelled remains harmless only because its aborted ownership must fail before scrolling/rescheduling. An already-cancelled operation does not require a user warning merely because native frame cancellation is unavailable.
2. **Missing RAF must give honest recovery.** V6's missing-RAF branch uses only the current `after.fits` to choose or clear the recovery hint. Earlier actual timeline evidence showed an initially fitting button becoming clipped later as native ArrowRight animation continued. Absence of the stabilization mechanism therefore cannot be declared successful from that one fitting measurement. Show the Day list fallback when RAF is absent unless an independently proved alternative supplies stabilization. Throwing RAF already enters the failure path; test both cases separately.
3. **A deadline without stable completion must not clear recovery.** V6 uses `!before.fits` at its one-second deadline, which can restore old help while a currently fitting rectangle remains unstable. Deadline expiration before the four-frame success condition means stabilization was not established. Preserve/show the Day list fallback; only actual stable completion may restore the saved help/role. Test moving-but-momentarily-fitting geometry as well as permanently clipped/no-op scrolling.

The root author agreed to these corrections in a superseding v7; v6 remains frozen. This reviewer did not implement them.
