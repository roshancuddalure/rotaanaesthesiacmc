# OT calendar and availability contract — November implementation

This records the implemented N07/N08/N10/N11 behavior. It does not assert that N12/N14 all-path protection, N13 monthly heatmaps, or clinical departmental acceptance are complete. The feature remains disabled by default until integration and rollout checks are ready.

## Inputs and precedence

- The calendar is per canonical unit. Weekly records carry a stable ID, area key, weekday (Monday–Sunday codes; UI displays Sunday–Saturday), inclusive effective dates, staffing roles and source reference. Every record must belong to its selected unit.
- Each staffing role has explicit start/end minutes, mandatory minimum, preferred target, call-level pool and optional reviewed skill codes. There is no inferred substitution between levels and no inferred supervision ratio. Different roles can represent separate staffing needs in the same area.
- Counts are strict whole numbers from 0 to 128, target is at least minimum, and call pools must be nonempty and distinct. Dates must be explicit calendar dates, never coerced Unix timestamps or datetime values.
- Start is within the named day; end may be the following day. A role lasts more than zero and at most 24 hours. One person covers a complete role band; handover must be represented explicitly by separate bands. Adjacent bands may share a person; simultaneous bands cannot, even across units.
- Weekly definitions for the same unit/area/weekday cannot have overlapping effective periods. A date exception replaces all weekly roles for that unit/area/date. It must either close the area or supply replacement roles; duplicate date exceptions are rejected.
- Monthly changes use bounded effective weekly definitions or explicit dated replacements. They do not silently outrank overlapping weekly records. Holiday dates do not automatically close OT areas; a reviewed dated closure/replacement is explicit.
- For an area known from an effective weekly definition, a missing weekday is unknown. If one area is defined on the selected day and another known area is not, the day is only partially configured. It cannot certify full OT coverage. An explicit closure or zero-count band is distinct from missing input. Dated additional areas do not become an invented recurring obligation on other dates.
- Reserve interpretation is an explicit administrator choice: `included` allows OT staff to satisfy a same-unit reserve; `additional` requires distinct people. The saved-day preview jointly evaluates OT and existing minima for each configured OT call pool. A single-level pool uses its existing call override; a pooled requirement uses the existing generic minimum. Unrelated call pools and other rota constraints still require full allocation validation.
- Overlapping same-unit reserve predicates may share a compatible person; minima are never blindly summed. Simultaneous OT roles are exclusive, and different units can never reserve the same identity simultaneously. Reserve counts may hand over at interval boundaries; a whole OT role requires one person throughout its band. Optional target coverage cannot consume mandatory reserve.

## Availability and feasibility

- `canonical_availability` reads canonical active people, inclusive dated postings, current and legacy call timelines, approved/pending leave and relevant active duties. Identity is deduplicated across overlapping postings; competing unresolved posting call levels produce a data-quality warning, not an arbitrary choice.
- Availability windows carry their exact unit, call level and explicitly supplied skill mapping. A midnight posting transfer or promotion cannot grant eligibility for an entire overnight role that the member only partly qualifies for. A promotion within an explicitly eligible multi-level pool remains eligible throughout.
- Approved leave blocks its actual interval. AM means 00:00–12:00, PM 12:00–24:00, NIGHT means 00:00–08:00 and 18:00–24:00 on each inclusive stored leave date. These preserve existing anchors while using actual OT-band overlap. The existing duty rule that any partial leave blocks a 24-hour duty remains separate and unchanged.
- Pending/imported-review leave remains visible but does not become approved automatically. A separately labeled pending-leave stress mode treats it as unavailable. Cancelled and rejected requests do not block either scenario.
- Saved and explicitly supplied provisional assignments block their actual duty interval, configured post-24-hour rest, and the existing duty-specific same-day/next-day elective flags. Queries include preceding months and extended rest windows. Cancelled assignments do not block.
- Multiple blocking causes are merged as interval unions. A person on both leave and post-duty rest is not subtracted twice. Marginal compatible-person counts are not summed to prove simultaneous coverage; the matcher enforces identity-level overlap constraints.
- Skills are never guessed from names, designations or eligibility-group labels. Administrators explicitly bind a skill key to existing active canonical groups in the calendar's reviewed/versioned configuration. Dated active membership grants that skill only in the bound unit/window; it never widens the allowed call pool. Unknown/inactive sources cannot be saved as new bindings. A missing binding or withdrawn source preventing coverage proof stays unresolved. Empty bindings preserve earlier no-op calendar hashes.
- Feasibility prioritizes mandatory coverage over optional targets. A timeout without full coverage is unresolved, not an infeasibility proof. A feasible result is only an OT reservation witness relative to these inputs, not an operational assignment or publication permission.
- Availability defaults to a 35-day bound. The new read-only monthly assignment adapter explicitly allows up to 45 days, including preceding overnight demand and future OT through the latest duty's actual end plus configured rest. Longer horizons remain unresolved rather than truncated. This adapter and its reusable guard are N14 foundations; operational entry-point integration remains unfinished.
- `ot_capacity_verify.py` independently checks identities, dated eligibility, interval continuity, sharing, mandatory/target counts and shortages. Solver agreement is not the proof. Resource limits and timeouts without full mandatory coverage remain unresolved.
- The immutable assignment guard overlays the complete final assignment set on leave/posting/qualification availability loaded without duties. It caches bounded private proofs, independently rechecks an existing witness before reusing it for changed blocks, and performs no database reads during candidate checks. Snapshot replacement starts a fresh cache. The loader must explicitly attest reviewed complete demand; an empty or partial input cannot certify closure by default.

### Balance replacement prechecks

With OT protection enabled, the balance planner's `free_one` precheck evaluates
the replacement after releasing the slot's current holders from the OT placement
calculation. Counting both donor and recipient incorrectly rejects a safe move.
This precheck grants no overwrite authority: the actual transfer removes its
precise assignment rows, checks the resulting plan, and runs the independent
post-write verification before commit. Other extra-duty placements retain their
ordinary additive reservation check.

OT-aware balance prechecks also depend on other people's reservation alternatives.
After any successful in-memory transfer, their placement memo is cleared for all
recipients. Personal version stamps alone cannot preserve a rejection after a
different specialist returns to OT. Failed transfers restore their original state;
the legacy path retains its existing personal-version cache behavior.

Clean cached input attributes/collections expire under the lock; primary identities and dirty caller attributes/relationships remain intact. The lock helper never flushes or commits. This prevents cached calendar/unit/rule state from surviving an intervening committed edit.
- Enabled template generation rereads draft/scope authority, units and effective read-only rules under the final lock, rather than reusing a pre-lock rule DTO. Legacy Safe Auto-Fill acquires the lock after its audit-run bootstrap commit and reloads period/slots before building its shared context. Normal reviewed apply still checks its current input fingerprint.
- First-use default groups/rule versions/settings flush within a protected scheduling transaction. A root-transaction marker controls bootstrap commit ownership and is never evidence that a database lock is held. Normal bootstrap behavior resumes after that transaction ends. This accounts for nested preview rollback without allowing an initializer to commit away an apply lock.

## Native editor and recovery

- Admin Tools → Unit OT Calendars uses the existing application framework/API client. It offers unit/weekday selection, area and multi-call roles, effective dates, weekday copy review, closures and multi-role dated replacements, saved history and saved-day role coverage.
- Every save requires a server-validated, side-by-side preview and explicit confirmation. Preview writes no calendar/history records. Editing during a pending preview invalidates that preview. Unfinished form entries must be added or cleared before review.
- Copy creates independent draft IDs and never silently overwrites overlapping destination definitions. Changes remain drafts until reviewed save. Leaving/switching unit protects unsaved drafts; a save in progress prevents navigation and Escape dismissal.
- Concurrent edits produce a conflict and preserve the local draft. The user can inspect the latest saved configuration, use it, or explicitly review replacing it. No silent rebase is performed.
- An uncertain save is checked by durable readback. Matching saved configuration confirms success. Failed readback blocks another save until an explicit successful read; no mutation is automatically replayed.
- Unit/read responses and capacity checks are scoped to the current host/unit. A delayed older preview cannot overwrite newer edits. A delayed earlier capacity response cannot replace a newer check. Read-only rules loading does not initialize defaults or commit operational changes.
